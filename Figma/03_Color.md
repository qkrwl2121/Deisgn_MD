# 컬러 가이드 문서 검토 및 컬러 토큰(Variables) 등록 가이드 (Figma)

Figma 디자인 파일 내 컬러 가이드 문서("03 Color" 프레임 등)를 검토하여, 그 내용을 Figma Variables(컬러 토큰)로 등록할 때 사용하는 규칙이다.

## 작업 프로세스 및 보고 규칙 (모든 점검·수정 공통)

이 문서 기준으로 점검·수정 작업을 진행할 때는 항상 아래 절차를 따른다.

1. **이해** — 사용자의 요청이 정확히 무엇을 대상으로 하는지(어떤 노드·프레임·범위) 파악한다.
2. **분석** — 이 문서에 정의된 규칙과 대상의 현재 상태를 비교해 어떤 항목을 확인해야 하는지 정리한다.
3. **탐색** — `get_metadata`/`use_figma` 등으로 실제 값을 전수 조사한다. 이 단계에서 겉보기 속성(예: `strokeWeight` 숫자값)만 보지 말고, 그 속성이 실제로 적용되고 있는지(예: `strokes` 배열이 비어있지 않은지)까지 확인한다 — 적용되지 않는 leftover 값을 오류로 오인하지 않도록 주의한다.
4. **계획** — 발견한 사항을 "값 자체가 규칙과 다른 경우"와 "값은 맞는데 반영/바인딩만 빠진 경우"로 구분해 정리한다.
5. **검증** — 결론을 내리기 전에 관련 레이어를 개별로 다시 확인(스크린샷·개별 노드 조회 등)해 오탐이 없는지 재확인한다.

**오류가 발견되면 어떤 경우에도 바로 수정하지 않는다.** 발견한 내용을 먼저 표/목록으로 사용자에게 보고하고, 사용자의 확인을 받은 뒤에만 수정을 진행한다. (이 문서의 다른 절에 "값만 같으면 확인 없이 바로 바인딩 가능" 같은 예외가 있더라도, 이 규칙이 우선한다.)

## 0. 두 가지 시나리오 — 어떤 절차를 쓸지 먼저 구분한다

이 문서는 방향이 반대인 두 절차를 모두 다룬다. 사용자 요청을 받으면 아래 기준으로 먼저 어느 쪽인지 판단하고, 애매하면 진행 전에 사용자에게 확인한다.

- **A. 가이드 → 프레임 적용** (아래 1~8번): **컬러 가이드 문서가 이미 정의돼 있고**, 그 값을 실제 화면(프레임)에 적용·바인딩하고 싶을 때. 예: "이 가이드 기준으로 컬러 적용해줘", "가이드 문서 보고 토큰 등록해줘"
- **B. 프레임 → 가이드 정의** (아래 9번, 역방향): **화면(메인 프레임)을 먼저 작업했고**, 거기서 실제 쓰인 색을 뽑아 가이드 문서·토큰 자체를 새로 정의/교체하고 싶을 때. 예: "메인에서 쓴 색 뽑아서 가이드에 반영해줘", "가이드를 메인 기준으로 새로 정의해줘"

두 절차 모두 결과물은 동일하게 Variables 등록 + 가이드 문서 반영 + 프레임 바인딩이지만, **출발점(가이드가 원본인지, 프레임이 원본인지)이 반대**라는 점이 핵심 차이다.

## 1. 가이드 문서 구조 파악

- 가이드 프레임의 `Contents` 하위에 있는 각 섹션(프레임)을 하나의 **그룹**으로 본다.
- 그룹명은 각 섹션의 **레이어명이 아니라, 섹션 안에 표시된 타이틀 텍스트**를 기준으로 한다.
  - 예: 레이어명은 여러 섹션이 동일하게 "02 Secondary Color"로 되어 있어도, 실제 타이틀 텍스트가 "Point Color"/"System" 등으로 다르면 그 타이틀 텍스트를 그룹명으로 쓴다.
- 섹션 안의 각 컬러 칩(스와치)이 실제 토큰 하나에 대응한다.

## 2. Primary Color 그룹 네이밍

- Primary Color 그룹 안에는 여러 개의 색상 계열(행)이 있을 수 있다 (예: Blue, Navy).
- 각 계열의 **메인 컬러칩 안에 표시된 이름**(예: `Blue`, `Navy`)을 그 계열의 이름으로 쓴다.
- 토큰명 형식: `{계열 이름} {숫자}`
  - 메인 컬러칩 = **100**
  - 나머지 그라데이션 칩들은 메인 다음으로 진한 것부터 **90, 80, 70 … 10**까지 내림차순으로 부여한다 (숫자가 클수록 진하고 메인에 가까움, 10이 가장 옅음).
- 예:
  ```
  Primary Color/Blue 100   (메인, 예: #25468F)
  Primary Color/Blue 90
  Primary Color/Blue 80
  ...
  Primary Color/Blue 10
  Primary Color/Navy 100   (메인, 예: #16233F)
  Primary Color/Navy 90
  ...
  Primary Color/Navy 10
  ```

## 3. Primary Color 외 그룹 네이밍

- Primary Color를 제외한 나머지 그룹(Point Color, Grays, Background Color, White, Line, System 등)의 토큰명은 **컬러 칩의 실제 hex 값**을 그대로 사용한다.
  - 예: `Point Color/#418DFF`
- **동일한 숫자(또는 알파벳)가 4개 이상 연속으로 반복되는 hex 값**은 3자리로 축약해서 이름에 쓴다.
  - 예: `#444444` → `#444`, `#666666` → `#666`, `#999999` → `#999`, `#EEEEEE` → `#EEE`, `#DDDDDD` → `#DDD`, `#CCCCCC` → `#CCC`, `#FFFFFF` → `#FFF`
  - 반복이 4개 미만이면(예: `#1A1A1A`) 축약하지 않고 전체 hex를 그대로 쓴다.
  - 단, 이 축약은 **토큰 이름 표기에만** 적용하고, 실제 저장되는 컬러 값은 원래 6자리 hex 그대로 사용한다.

## 4. System 컬러 예외 규칙

- System 그룹의 컬러가 **붉은 계열(빨강/레드 계열)일 경우**, 토큰명에 `Error`를 병기한다.
  - 형식: `System/Error` (hex 값은 이름에 붙이지 않고 값으로만 저장)

## 5. 등록 절차 (Figma MCP 기준)

1. `get_metadata`로 가이드 프레임(예: "03 Color") 구조를 조회하여 `Contents` 하위 섹션 목록과 각 섹션의 타이틀 텍스트를 파악한다.
2. 각 섹션의 컬러칩 노드를 `use_figma`로 순회하며 **실제 fill 값**을 직접 조회한다.
   - 스와치 옆의 hex 텍스트 라벨은 실제 fill 값과 다를 수 있으므로 **라벨을 신뢰하지 말고 fill을 직접 확인**한다.
   - 예: Background 섹션의 텍스트 라벨은 `#F6F8F9`였지만 실제 fill은 `#F6F7FA`였던 사례가 있었다.
3. 2번 기준 위 1~4번 네이밍 규칙에 따라 등록할 토큰명·값 목록을 작성한다.
4. **기존에 등록된 Color 컬렉션의 변수를 전량 삭제**한다 (`figma.variables.getLocalVariableCollectionsAsync()` → 대상 컬렉션의 `variableIds` 전체를 `getVariableByIdAsync` 후 `.remove()`).
   - 단, 사용자가 삭제 없이 추가만 요청한 경우에는 이 단계를 생략한다.
5. `figma.variables.createVariable(name, collection, "COLOR")`로 신규 변수를 생성하고, `setValueForMode`로 RGB 값을 지정한다.
   - `scopes`는 **`["ALL_SCOPES"]`로 명시 설정한다.** (과거에 `ALL_FILLS`로만 좁혀 등록했다가 Stroke 패널에 토큰이 안 뜨는 문제가 있었음 — `ALL_FILLS`는 Fill 계열만 포함하고 `STROKE_COLOR`는 별도 스코프라 Stroke에는 노출되지 않는다.) Fill/Stroke/Effect 등 어디서든 바인딩 가능하도록 컬러 토큰은 항상 전체 스코프로 등록한다.
   - 변수명은 `그룹명/칩이름` 형식으로 지정하면 Figma Variables 패널에서 자동으로 그룹명 폴더 아래에 정리된다.
6. 생성된 변수를 `getVariableByIdAsync`로 재조회하여 이름·값이 의도대로 등록됐는지 검증한다.

## 6. 컬러 토큰 적용(바인딩) 절차 — 실제 프레임에 매치

등록된 컬러 토큰(Variables)을 실제 디자인 프레임의 fill/stroke에 연결(바인딩)할 때 따르는 절차다.

1. 대상 프레임의 모든 노드를 순회하며 SOLID fill/stroke 색상을 hex 값과 노드 ID 기준으로 전수 추출한다. 이미 변수에 바인딩된 항목(`boundVariables.color` 존재)은 제외한다.
2. **정확히 일치하는 색상부터 먼저 바인딩한다.** 추출한 hex가 등록된 토큰 값과 **완전히 동일한 경우**, `figma.variables.setBoundVariableForPaint(paint, "color", variable)`로 바인딩한다. 이 단계는 시각적 변화가 전혀 없으므로 바로 진행해도 된다.
   - `setBoundVariableForPaint`는 새 paint 객체를 반환하므로 반드시 반환값을 `fills`/`strokes` 배열에 재할당해야 한다.
3. **정확히 일치하지 않는 색상은 근사값(가장 가까운 토큰) 매칭을 계산**한다. Lab 색공간 기준 ΔE(색차)를 구해 가장 가까운 토큰을 찾는다.
4. **근사값으로 바인딩하기 전, 반드시 먼저 사용자에게 보고하고 확인을 받는다** (아래 7번 참고). 확인 없이 근사값으로 임의 변경하지 않는다.
5. 사용자가 승인한 항목만 근사값 토큰에 바인딩한다. 배너/그리드 가이드 등 **실제 디자인 의도가 있는 색상이나 콘텐츠가 아닌 요소(그리드·재단선 가이드 등)는 확인 후에도 제외 대상이 될 수 있다.**
6. **인스턴스 내부 오버라이드 노드(ID에 `;`가 포함된 노드, 예: `I458:2951;361:2451`)는 일반 노드와 분리해서 별도 스크립트로 처리한다.** 일반 노드와 함께 한 스크립트에서 순회하며 바인딩하면 `"The node with id X does not exist"` 오류가 발생하며 스크립트 전체가 롤백될 수 있었다. 먼저 `!n.id.includes(";")`로 일반 노드만 처리하고, 인스턴스 오버라이드 노드는 이후 별도 스크립트에서 처리한다.
   - **단, 같은 마스터 컴포넌트를 공유하는 인스턴스가 여러 곳(예: Header/Footer가 여러 프레임에 반복 배치)에 있다면, 각 인스턴스 오버라이드에 개별 바인딩하지 않는다.** `instance.getMainComponentAsync()`로 원본을 찾아 **마스터에 한 번만 바인딩**하고, 인스턴스는 상속받도록 한다(Style_Guide.md 0번 공통 규칙 참고). 인스턴스별 개별 바인딩은 마스터가 바뀌어도 반영되지 않아 의미가 없다.
7. 바인딩 후 `get_screenshot`으로 대상 프레임을 렌더링해 시각적으로 깨진 부분이 없는지 확인한다.

## 7. 근사값 바인딩 전 필수 확인 절차 (작업 방식)

- 등록된 토큰과 **정확히 일치하지 않는 색상**을 근사값으로 바인딩하기 전에는, 아래 내용을 표로 정리해 사용자에게 먼저 보고한다.
  - 일치하지 않는 hex 값, 사용 횟수, 사용처(노드명/역할)
  - (가능하면) 가장 가까운 토큰 후보와 색차(ΔE) 정도
- 사용자의 확인/승인을 받은 뒤에만 근사값 바인딩을 진행한다. **먼저 묻지 않고 임의로 근사값으로 교체하지 않는다.**
- 이 절차는 Color 토큰뿐 아니라, 향후 다른 종류의 값(폰트, 간격 등)을 근사값으로 통일할 때도 동일하게 적용한다.

## 8. 오류 판정 기준

- 그룹명이 가이드 섹션의 실제 타이틀 텍스트와 다름 (레이어명을 그대로 사용한 경우 포함)
- Primary Color 토큰명이 `{계열 이름} {숫자}` 형식이 아니거나, 메인 컬러가 100이 아니거나, 90~10이 내림차순(진한 순)으로 배열되지 않음
- Primary Color 외 그룹의 토큰명이 실제 hex 값과 다름 (3번 규칙의 축약 예외는 허용)
- 4개 미만 반복되는 hex를 임의로 축약했거나, 4개 이상 반복되는데 축약하지 않음
- System 컬러가 붉은 계열인데 토큰명에 `Error`가 없음
- 텍스트 라벨만 보고 실제 fill 값을 확인하지 않은 채 값을 등록함
- 신규 토큰 등록 전, 삭제가 필요한 상황인데 기존 토큰을 삭제하지 않고 중복 등록함
- **정확히 일치하지 않는 색상을 사용자 확인 없이 근사값 토큰으로 임의 바인딩함**
- 인스턴스 내부 오버라이드 노드를 일반 노드와 한 스크립트에서 함께 순회하다 오류로 전체 바인딩이 롤백됨
- 가이드 문서와 Variables 양쪽 중 한쪽만 수정하고 다른 쪽(그룹/토큰 삭제, 스와치 값 등)을 누락함
- Variables 패널의 표시 순서가 가이드 문서에 보이는 순서와 다름
- 컬러 토큰의 `scopes`가 `ALL_SCOPES`가 아닌 값(예: `ALL_FILLS`만)으로 좁게 설정되어 Fill 외의 속성(Stroke 등)에서 토큰이 노출되지 않음

## 9. 메인 프레임 기준으로 가이드 컬러를 새로 정의하는 절차 (역방향)

5~7번 절차는 "가이드가 이미 정의돼 있고, 그 값을 프레임에 적용"하는 방향이다. 반대로 **새 프로젝트에서 메인 프레임을 먼저 작업한 뒤, 그 안에서 실제 쓰인 색을 뽑아 가이드(Primary Color/Grays 등)를 새로 정의**해야 하는 경우 아래 절차를 따른다. 이 경우 가이드 프레임에 미리 붙여넣어진 색(예: 다른 프로젝트에서 복사된 Blue/Navy 템플릿 값)은 참고용일 뿐, 실제 메인 프레임의 색과 다르면 그대로 두지 않는다.

1. **메인 프레임의 실제 사용 색상 전수 추출**: 대상 프레임(`main` 등)의 모든 노드를 순회하며 SOLID fill/stroke를 hex 기준으로 집계한다(사용 횟수·사용처 노드명 포함).
2. **Primary/Grays 분류**: 추출된 색 중 무채색(검정·흰색·회색 계열)이 아닌, 브랜드를 대표하는 색이 있으면 그것을 **Primary**로 분류한다. 나머지 텍스트·아이콘 등에 쓰인 무채색은 **Grays**로 분류한다.
   - 판단이 애매하면(색이 여러 개거나, Primary로 볼 색이 아예 없는 경우 등) 사용자에게 먼저 확인한다.
3. **placeholder 색 제외**: 사진이 아직 안 들어간 이미지 자리의 기본 배경색(피그마 기본 사각형 색 `#D9D9D9` 등, 실제 화면에서 사진에 가려져 보이지 않는 값)은 팔레트에서 제외한다. 제외 여부가 애매하면 스크린샷으로 실제 노출 여부를 확인하고, 그래도 애매하면 사용자에게 먼저 물어본다.
4. **근접한 무채색 통합 여부 확인**: `#000000`/`#050505`처럼 육안으로 구분 안 되는 값이 여러 개 섞여 있으면, 통합할지 개별 유지할지 사용자에게 먼저 확인한다.
5. **Primary 그라데이션 자동 생성**: Primary로 정한 메인 컬러(레벨 100)를 기준으로 90~10 단계를 아래 공식으로 계산한다 (기존 가이드의 Blue/Navy 스케일을 역산해서 찾은 공식).
   ```
   p = (100 - level) / 100         // level: 90,80,...,10
   levelColor = mainColor * (1 - p) + white * p   // 채널별 선형 보간, 흰색과 섞음
   ```
   - 예: 메인이 `#258052`면 레벨90=`#3B8D63`, 레벨10=`#E9F2EE` 방향으로 점점 흰색에 가까워진다.
6. **가이드 문서 자체를 실제 값으로 교체**: 가이드 프레임의 기존 스와치(fill·이름 텍스트·hex 텍스트)를 새로 정의한 값으로 갱신한다.
   - 먼저 대상 컨테이너의 `layoutMode`를 확인한다. **auto-layout(HORIZONTAL/VERTICAL + AUTO 사이징)인 경우, 불필요한 행/칩 노드를 그냥 삭제하면 하위 형제들이 자동으로 reflow된다** — 수동으로 좌표를 재계산할 필요가 없다. auto-layout이 아니면 삭제 후 남은 요소들의 좌표를 직접 재조정해야 한다.
   - 사용하지 않는 그룹(예: 메인에 전혀 안 쓰인 Point Color, Background Color, System)은 섹션 전체를 삭제한다.
7. **미사용 그룹·토큰은 Variables에서도 함께 삭제한다.** 가이드 문서에서 섹션/칩을 지웠다면, 대응하는 Figma Variable도 반드시 같이 삭제한다 (문서만 지우고 토큰을 남겨두는 실수에 주의).
8. **가이드 문서의 스와치 자체도 Variables에 바인딩한다.** 5~7번 절차(기존 가이드→프레임 적용)에서는 프레임에만 바인딩했지만, 이 역방향 절차에서는 가이드 프레임의 스와치도 새로 만든 토큰에 `setBoundVariableForPaint`로 바인딩해서 가이드 문서가 토큰 값을 그대로 반영하도록 만든다.
   - 그룹처럼 보이지만 실제로는 `GROUP` 타입이라 `fills` 프로퍼티가 없는 wrapper 노드가 있을 수 있다. 바인딩 대상은 반드시 실제 `RECTANGLE`(또는 fills를 가진) 노드인지 확인한다.
9. **Variables 표시 순서를 가이드 문서 노출 순서와 일치시킨다.** Figma Variables는 Text Style과 마찬가지로 **별도의 정렬 API가 없고 생성된 순서대로 패널에 표시**된다. 순서를 맞추려면:
   1. 현재 대상 프레임·가이드 프레임에서 각 토큰이 바인딩된 노드 목록(노드ID·prop·index)을 전수 스캔해 기록한다.
   2. 기존 변수를 전량 삭제한다.
   3. 가이드에 보이는 순서(위→아래, 왼→오)대로 변수를 다시 생성한다.
   4. 1번에서 기록한 바인딩을 새로 생성된 변수에 다시 연결한다.
10. 바인딩 후 `get_screenshot`으로 메인 프레임과 가이드 프레임 양쪽을 렌더링해 검증한다.

## 10. "Foundations" 컬렉션 — 팔레트 문서용 계층형 네이밍 (별도 절차)

3-1 절(팔레트 문서, "03-1 Color (Palette)" 프레임처럼 계열별로 100~10 스케일이 여러 개 반복되는 구조)의 스와치를 Variables로 등록할 때 쓰는 절차다. 2~3번의 `{계열 이름} {숫자}`(공백 구분, 기존 "Color" 컬렉션) 방식과는 별개로, **"Foundations"라는 새 컬렉션**을 만들고 그 안에 `/`로 완전히 계층화된 이름을 쓴다.

- 변수명 형식: `Color/{그룹명}/{칩 라벨}`
  - 예: `Color/Blue/100`, `Color/Navy/10`, `Color/Functional/Red`, `Color/Neutral/1A1A1A`, `Color/Cool Neutral/100`, `Color/White/90`
  - Figma Variables 패널에서 `/`는 폴더 구분자로 동작하므로, 컬렉션 탭 "Foundations" 안에 `Color` 폴더 → 각 그룹 폴더 → 칩 라벨 순으로 중첩되어 "Foundations > Color > Blue > 100" 형태로 보인다.
  - 그룹명이 여러 단어면(`Cool Neutral`) 공백을 그대로 쓴다.
  - 칩 라벨은 100~10 스케일 그룹(Blue/Navy/Sky/Cool Neutral/White)은 숫자 그대로, Functional처럼 색상명으로 구분되는 그룹은 색상명(Red/Orange/...) 그대로, Neutral처럼 hex로 라벨링된 그룹은 hex 값(축약 없이) 그대로 쓴다.
- 값은 스와치의 **실제 fill**(`rect.fills[0].color`)을 그대로 쓰고, opacity가 100%가 아니면(예: White의 90~10) alpha 채널에 그 값을 넣는다(`{r,g,b,a}`).
- `scopes`는 5번 절차와 동일하게 `ALL_SCOPES`로 등록한다.
- **기존 "Color" 컬렉션은 건드리지 않는다.** "Foundations"는 별도 컬렉션으로 추가되는 것이며, 사용자가 명시적으로 요청하지 않는 한 기존 컬렉션의 변수를 이 절차로 삭제·대체하지 않는다.
- 등록 순서: 각 그룹을 스캔한 순서(Blue→Navy→Sky→Functional→Neutral→Cool Neutral→White) 그대로 생성해, Variables 패널 표시 순서가 가이드 문서 섹션 순서와 일치하도록 한다.

## 11. "03-2 Color (Semantic)" — 시맨틱 컬러 토큰 계층 (별도 절차)

기존 "Color" 컬렉션(2~8번 절차)은 이후 **시맨틱(의미) 이름 체계**로 전환되었다. 더 이상 hex 값을 이름에 쓰지 않고, **역할/의미를 이름으로 쓰고 값은 10번 절차의 "Foundations" 컬렉션(원시 팔레트)을 `VARIABLE_ALIAS`로 참조**하는 2단(원시→시맨틱) 토큰 구조다. 가이드 프레임 "03-2 Color (Semantic)"이 이 시맨틱 계층을 시각화한 문서다.

- 변수명 형식: `{역할 그룹}/{상태}` (예: `Primary/Normal`, `Primary/Heavy`, `Primary/Point`, `Font/Strong`, `Font/Secondary`, `Font/Tertiary`, `Font/Subtle`, `Font/Disabled`, `Font/White`, `Label/Bg-Normal`, `Label/Bg-Heavy`, `Label/Bg-Sky`, `Label/Font-Normal`, `Label/Font-Blue`, `Label/Font-White`, `Background Color/Normal`, `Background Color/Point`, `Background Color/Heavy`, `Background Color/Disabled`, `Line/Normal`, `Line/Neutral`, `Line/Heavy`, `System/Error`).
- 값은 직접 RGB를 넣지 않고, `figma.variables.createVariable`로 만든 뒤 `setValueForMode`에 `{ type: "VARIABLE_ALIAS", id: 원시토큰ID }` 형태로 "Foundations" 컬렉션의 변수를 가리키게 한다. 이렇게 하면 원시 팔레트 값이 나중에 바뀌어도 시맨틱 토큰이 자동으로 따라간다.
- `scopes`는 기존과 동일하게 `["ALL_SCOPES"]`.
- 가이드 문서(스와치)는 각 칩의 `fills`를 시맨틱 변수에 직접 바인딩한다(원시 Foundations 변수가 아니라 반드시 시맨틱 변수 쪽에 바인딩 — 칩이 나타내는 것은 시맨틱 의미이기 때문).
- **검증 시 라벨/레이어명만 보지 말고, 실제 `boundVariables.fills[0].id`가 의도한 시맨틱 변수 id와 일치하는지 확인한다.** 겉보기엔 정상 색상이어도 (a) 아예 바인딩이 안 돼있거나(raw fill만 값이 우연히 일치), (b) 삭제된 옛 변수 id에 매달려 있거나(재생성으로 id가 바뀌었는데 재바인딩이 안 된 경우), (c) 시맨틱이 아닌 Foundations 원시 변수에 잘못 바인딩된 경우가 섞여 있을 수 있다 — 이 세 가지 모두 값은 맞아 보이지만 토큰 체계상 오류다.
- Variables 컬렉션에 존재하는 변수 목록과 가이드 문서의 스와치 목록을 **양방향으로 대조**한다. 가이드에 없는 변수(신규 추가됐는데 가이드 반영이 누락된 경우)가 있으면 가이드 문서에 스와치를 추가해야 하고, 가이드에 있는데 변수가 없으면(변수가 삭제됐거나 이름이 바뀐 경우) 가이드 라벨을 갱신하거나 스와치를 제거해야 한다.

### 11-1. 현행화(Variables → 가이드 동기화) 절차

기존 가이드 문서가 Variables의 시맨틱 "Color" 컬렉션과 어긋나 있을 때(스와치는 있는데 바인딩이 빠졌거나, 값은 맞는데 연결이 죽어있거나, 변수가 추가/삭제됐는데 가이드에 반영이 안 된 경우 등) 실제로 동기화한 순서다.

1. `figma.variables.getLocalVariableCollectionsAsync()`로 "Color" 컬렉션을 찾아 `variableIds`를 전부 `getVariableByIdAsync`로 조회, **변수명 → 변수 객체** 맵을 만든다.
2. 가이드 프레임을 `get_metadata`로 조회해 각 섹션의 스와치(rect 노드)를 변수명과 1:1로 매핑한 표를 수동으로 작성한다(섹션 타이틀 텍스트 + 칩 라벨 텍스트를 조합해 어떤 변수에 대응하는지 판단).
3. 매핑한 각 스와치에 대해 스크립트로 `node.boundVariables.fills[0].id`(현재 실제 바인딩 id)를 조회하고, 1번 맵에서 찾은 **기대 변수 id**와 비교한다. 불일치를 다음 세 유형으로 분류한다.
   - 바인딩 자체가 없음(raw fill만 값이 우연히 같음)
   - 바인딩은 있지만 가리키는 id가 존재하지 않거나(삭제된 변수) 다른 이름의 변수임(재생성으로 id가 바뀐 경우 등)
   - 바인딩이 시맨틱 변수가 아니라 Foundations 원시 변수 등 **다른 컬렉션의 변수**를 가리킴
4. 값 자체도 함께 검증한다 — 시맨틱 변수의 값이 `VARIABLE_ALIAS`면 그 원본(Foundations 변수)까지 재귀적으로 resolve해서 최종 RGB를 구하고, 스와치의 현재 raw fill과 소수 셋째 자리까지 비교해 진짜 색상 드리프트가 있는지도 확인한다(바인딩 문제와 별개로 값 자체가 틀렸을 가능성도 배제하지 않기 위함).
5. 1번 변수 맵과 2번 스와치 매핑을 양방향으로 diff해서 **가이드에 스와치가 없는 변수**(신규 추가분)와 **변수가 없는데 가이드에 남은 스와치**(삭제/개명분)를 찾는다.
6. 텍스트를 수정해야 하면 먼저 `figma.loadFontAsync({ family, style })`로 해당 텍스트의 폰트를 로드한 뒤 `characters`를 바꾼다(로드 없이 바로 쓰면 `unloaded font` 오류).
7. 불일치 스와치는 `figma.variables.setBoundVariableForPaint(paint, "color", variable)`로 재바인딩하고 그 반환값을 `node.fills`에 재할당한다(`node.setBoundVariable("fills", ...)`는 fills/strokes에는 쓸 수 없고 paint 단위로만 바인딩 가능 — 바로 시도하면 오류 발생).
8. 신규 스와치가 필요하면 같은 섹션의 기존 칩(구조가 동일한 것)을 `clone()`해서 위치·라벨·바인딩만 바꾸는 방식으로 만든다. 그리드 형태 섹션(예: 3열 → 4열)이면 부모 컨테이너와 섹션 타이틀 텍스트의 `width`도 늘어난 칸 수에 맞춰 `resize()`한다.
9. 라벨 텍스트가 실제 변수명과 다르면(리네이밍 누락 등) 텍스트만 정정하고 바인딩은 그대로 둔다.
10. 마지막에 전체 스와치를 다시 조회해 `boundVariables.fills[0].id`가 1번 맵의 기대값과 전부 일치하는지 재검증하고, 불일치 0건을 확인한 뒤 마무리한다.
