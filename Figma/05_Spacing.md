# Spacing(Division Spacing) 가이드 (Figma)

프로젝트의 여백·간격(Division Spacing) 값을 관리하는 규칙이다. 가이드 문서(비주얼 룰러, "05 Spacing" 프레임)와 Figma Variables("Spacing" 컬렉션, FLOAT)를 동기화하고, 실제 프레임의 auto-layout 속성(itemSpacing/padding)에 바인딩하는 절차를 다룬다.

> Grid(그리드) 관련 규칙은 `02_Layout.md`로 분리되어 있다. 이 문서는 **Division Spacing(간격)** 만 다룬다.

## 작업 프로세스 및 보고 규칙 (모든 점검·수정 공통)

이 문서 기준으로 점검·수정 작업을 진행할 때는 항상 아래 절차를 따른다.

1. **이해** — 사용자의 요청이 정확히 무엇을 대상으로 하는지(어떤 노드·프레임·범위) 파악한다.
2. **분석** — 이 문서에 정의된 규칙과 대상의 현재 상태를 비교해 어떤 항목을 확인해야 하는지 정리한다.
3. **탐색** — `get_metadata`/`use_figma` 등으로 실제 값을 전수 조사한다. 이 단계에서 겉보기 속성(예: `strokeWeight` 숫자값)만 보지 말고, 그 속성이 실제로 적용되고 있는지(예: `strokes` 배열이 비어있지 않은지)까지 확인한다 — 적용되지 않는 leftover 값을 오류로 오인하지 않도록 주의한다.
4. **계획** — 발견한 사항을 "값 자체가 규칙과 다른 경우"와 "값은 맞는데 반영/바인딩만 빠진 경우"로 구분해 정리한다.
5. **검증** — 결론을 내리기 전에 관련 레이어를 개별로 다시 확인(스크린샷·개별 노드 조회 등)해 오탐이 없는지 재확인한다.

**오류가 발견되면 어떤 경우에도 바로 수정하지 않는다.** 발견한 내용을 먼저 표/목록으로 사용자에게 보고하고, 사용자의 확인을 받은 뒤에만 수정을 진행한다. (이 문서의 다른 절에 "값만 같으면 확인 없이 바로 바인딩 가능" 같은 예외가 있더라도, 이 규칙이 우선한다.)

## 0. 기본 규칙

- 사이즈 및 간격은 **4 또는 8의 배수**로 지정한다.
- Division Spacing은 **컨텐츠 영역 안에서 객체 간 간격**을 정의하며, 전체 디자인의 통일성을 위해 아래 기준값을 우선 사용한다: `4, 8, 12, 16, 20, 24, 28, 32, 40, 48, 60, 64, 72, 80, 100, 120`
  - 페이지 바깥 레이아웃 마진(예: Header/Footer 좌우 360px 여백)은 "객체 간 간격"이 아니라 별도 카테고리이므로 이 기준값 목록에 포함하지 않는다.
- 위 기준값 외 별도 사이즈가 필요한 경우, 4 또는 8의 배수로 유연하게 적용한다 — 기준값 목록에 없다고 해서 그 자체로 오류는 아니다. 다만 실사용이 확인되면 기준값 목록·가이드·Variables에 반영한다(아래 2번 절차).
- Figma Variables 컬렉션 이름: `Spacing`, 변수명 형식: `Spacing/{값}` (예: `Spacing/24`) — Color 토큰이 hex 값을 이름에 그대로 쓰는 것과 같은 철학으로, 의미 이름(xs/sm/lg 등)이 아니라 실제 px 값을 이름에 쓴다.
- `scopes`는 `["ALL_SCOPES"]`로 설정한다 (특정 속성에만 좁혀 등록하면 다른 속성에 바인딩이 안 될 수 있다 — Color 토큰과 동일한 이유, `03_Color.md` 참고).

## 1. 가이드 문서 구조

원본: "05 Spacing" 프레임 → "03_Division Spacing" 섹션 (예: node-id `776:4673`)

- 상단 설명 텍스트: "사이즈 및 간격은 4 또는 8의 배수로 값을 지정합니다", "Division Spacing은 컨텐츠 영역 안에서 객체의 간격을 정의하며..."
- "Spacing"(GROUP) 안에 "Frame 1"(VERTICAL auto-layout, `itemSpacing: 20`, `primaryAxisSizingMode: AUTO`)이 있고, 그 자식으로 값 개수만큼 사각형(rectangle)이 오름차순으로 쌓여 있다.
  - 각 사각형은 **width 고정(1110), height = 실제 스페이싱 값**으로 그 값의 크기를 시각적으로 표현한다.
  - `itemSpacing: 20`이 자동으로 사각형 사이 간격을 만들어주므로, 자식을 추가/삭제만 하면 나머지는 auto-layout이 재배치한다.
- 각 사각형 오른쪽에 값 라벨(TEXT, 예: "4", "24", "120")이 있으며, 이 라벨은 **"Spacing" 그룹의 좌표계 기준으로 절대 배치**되어 있다(Frame 1의 자식이 아니라 형제).

## 2. 프레임에서 실제 사용 값 추출하는 절차 (전수 스캔)

메인 프레임(들)에서 실제 쓰이는 spacing 값을 뽑아 가이드/Variables와 동기화할 때는 아래 절차를 따른다.

1. 대상 프레임(들)의 모든 auto-layout 노드(`layoutMode !== "NONE"`)를 순회하며 `itemSpacing`, `paddingTop/Right/Bottom/Left`, (WRAP인 경우) `counterAxisSpacing` 값을 수집한다.
2. **일반 노드와 인스턴스 오버라이드 노드(`id`에 `;` 포함) 모두 포함해서 스캔한다.** 컴포넌트 내부(예: 카드 컴포넌트의 padding, Footer 내부 링크 간격 등)에만 존재하는 값도 실사용으로 인정한다 — 최상위 구조 프레임만 보면 실제 쓰이는 값을 놓칠 수 있다 (예: `Board/Main/Question`·`Board/Sub/Q&AList` 컴포넌트 내부의 28px, Footer의 `-- Links` 내부 64px는 최상위 스캔에서 누락된 적이 있었음).
3. **제외 대상**:
   - `primaryAxisAlignItems === "SPACE_BETWEEN"`인 노드의 `itemSpacing` — Figma가 콘텐츠 폭에 따라 자동 계산해서 보여주는 값이라 디자이너가 지정한 고정 토큰이 아니다 (수백~수천 단위의 비정상적인 값으로 나타난다).
   - `layoutWrap !== "WRAP"`인 노드의 `counterAxisSpacing` — 실제 레이아웃에 영향을 주지 않는 값일 수 있다.
   - `0` — 간격 없음은 토큰이 아니다.
   - 디자인 규칙(4 또는 8의 배수)에 맞지 않는 값(예: 아이콘 내부 패딩의 미세 조정 값 1건짜리) — 시스템 토큰이 아닌 컴포넌트 자체의 미세 조정으로 간주.
4. 남은 값 중 **가이드가 정의하는 범위(Division Spacing = 콘텐츠 내 객체 간 간격)에 해당하는지**와 **페이지 바깥 마진처럼 별도 카테고리인지**를 구분한다. 애매하면(예: 큰 값이 마진인지 간격인지) 사용자에게 먼저 확인한다.
5. 추출된 값과 기존 가이드/Variables 값을 비교해 **추가 대상**(실사용 있음, 가이드/Variables에 없음)과 **삭제 후보**(가이드/Variables에 있음, 실사용 없음)를 표로 정리해 사용자에게 먼저 보고하고, 승인받은 뒤 반영한다 (근사값 바인딩과 마찬가지로 삭제·불일치 항목은 항상 먼저 확인).
   - 4/8의 배수 규칙을 아예 어기는 값이 발견되면(예: 1px, 10px, 11px, 19px 등) 자동으로 보정하지 않고 사용자에게 별도 보고한다. 사용자가 승인한 항목만 규칙에 맞는 값으로 보정 후 반영한다.

## 3. 가이드 문서(룰러 다이어그램) 반영 절차

1. "Frame 1"의 기존 사각형 자식을 전량 삭제한다.
2. 최종 확정된 값 목록을 오름차순 정렬한 뒤, 각 값마다 기존 사각형 하나를 clone하여 스타일(fill 등)을 유지한 채 `resize(1110, 값)`으로 높이만 바꾸고 `appendChild`한다. `itemSpacing: 20`인 auto-layout이라 사각형 사이 간격은 자동으로 처리된다.
3. 라벨(TEXT)도 기존 라벨 전량 삭제 후 다시 만든다. 각 라벨의 위치는:
   - `x`: 자릿수 기준으로 기존 관례를 따른다 — 1자리 `1134`, 2자리 `1135`, 3자리 `1131` (기존 라벨 좌표를 참고해 정한 값, 자릿수에 따라 폭이 달라져 미세 조정됨).
   - `y`: `Frame 1의 y오프셋 + 사각형의 로컬 y + 사각형 높이/2 - 라벨 높이/2` (즉 사각형 세로 중앙에 라벨 텍스트가 오도록 정렬).
4. 최상위 "05 Spacing" 프레임은 `layoutMode: NONE`(auto-layout 아님)이라 콘텐츠가 바뀌면 **수동으로 높이를 재계산**해야 한다. 모든 자식의 `y + height` 중 최댓값에 하단 여백(기본 100px)을 더해 `resize`한다 (하위 auto-layout 컨테이너인 "03_Division Spacing"과 "Spacing" 그룹은 자동으로 크기가 조정되므로 별도 처리 불필요).
5. `get_screenshot`으로 렌더링 확인.

## 4. Variables 동기화 절차

1. `figma.variables.getLocalVariableCollectionsAsync()`로 "Spacing" 컬렉션(FLOAT 타입)을 찾는다.
2. 최종 확정된 값 목록과 기존 등록된 변수를 비교한다.
3. 없는 값은 `figma.variables.createVariable("Spacing/{값}", collection, "FLOAT")`로 생성하고 `setValueForMode`로 값을 지정한다. `scopes`는 `["ALL_SCOPES"]`로 설정한다.
4. 실사용이 없는 값은 변수를 삭제하되, **삭제 전 반드시 사용자에게 먼저 보고하고 확인받는다.** 삭제 전에는 해당 변수가 실제로 어딘가에 바인딩되어 있는지(전체 대상 프레임 + 마스터 컴포넌트 기준) 먼저 스캔해서, 끊어지는 바인딩이 있는지 확인하고 그 결과도 함께 보고한다.
5. 변수명은 `Spacing/{값}` 형식(예: `Spacing/24`)으로 통일한다.

### 정렬 규칙

Figma 로컬 Variables 패널은 변수가 **생성된 순서**대로 표시된다(별도의 sortPosition API 없음. Text Style과 동일한 제약, `04_2Font_Name.md` 정렬 규칙 참고). 따라서 Spacing Variables는 항상 **값 오름차순(작은 값 → 큰 값)** 으로 패널에 표시되도록 생성 순서를 관리한다.

- 새 값을 추가할 때 기존 변수 뒤에 그냥 이어 붙이지 않는다. 반드시 **기존 변수를 전량 삭제한 뒤, 전체 값을 오름차순으로 정렬해서 처음부터 다시 생성**하고, 기존에 각 변수에 바인딩되어 있던 노드·필드를 새로 생성된 변수 ID에 재연결한다.
  - 절차: ① 재생성 전, 현재 바인딩된 모든 노드의 (노드ID, 필드, 값) 목록을 전수 스캔해 기록 → ② 기존 `Spacing/*` 변수 전량 삭제 → ③ 오름차순으로 재생성 → ④ ①에서 기록한 바인딩을 새 변수 ID로 재연결 → ⑤ 값이 그대로 유지됐는지(시각적 변화 없음) 검증.
  - 마스터 우선 바인딩 규칙(`Style_Guide.md` 0번)과 함께 적용한다 — 재바인딩 시에도 인스턴스가 아닌 마스터 쪽에 연결한다.
  - 단, Figma UI에서 사람이 Local Variables 패널을 직접 드래그해 순서를 바꾸는 것은 가능하다(변수 id 유지, 재바인딩 불필요) — `04_2Font_Name.md` 정렬 규칙의 동일한 예외가 적용된다.

## 5. 프레임에 Variables 바인딩하는 절차

1. 대상 프레임의 auto-layout 노드를 순회하며(2번 절차와 동일하게 일반 노드 + 인스턴스 오버라이드 노드 모두 포함, SPACE_BETWEEN·0·범위 밖 값 제외) `itemSpacing`/`paddingTop`/`paddingRight`/`paddingBottom`/`paddingLeft` 값이 등록된 Spacing 변수와 정확히 일치하는지 확인한다.
2. 일치하면 `node.setBoundVariable(필드명, variable)`로 바인딩한다. 필드명은 `"itemSpacing"`, `"paddingLeft"`, `"paddingRight"`, `"paddingTop"`, `"paddingBottom"`(WRAP인 경우 `"counterAxisSpacing"`도 가능)을 그대로 사용한다.
3. **반복되는 컴포넌트 인스턴스 내부 요소(ID에 `;`가 포함된 노드)는 인스턴스 각각에 개별 바인딩하지 않는다.** 같은 마스터(예: Header, Footer)가 여러 프레임에 인스턴스로 반복 배치된 경우, `getMainComponentAsync()`로 원본을 찾아 **마스터 쪽 padding/itemSpacing에 한 번만 바인딩**하고 인스턴스는 상속받도록 한다. 이미 인스턴스마다 개별 바인딩이 걸려있었다면 마스터 바인딩 후 인스턴스의 로컬 바인딩은 해제한다 (`Style_Guide.md` 0번 공통 규칙 참고).
4. **일반 노드와 인스턴스 오버라이드 노드는 반드시 별도의 스크립트 호출로 나눠 처리한다.** 한 스크립트에서 함께 순회하다 하나라도 실패하면 전체가 롤백되는 문제가 Color/Font 작업에서 반복적으로 확인됐다 (`03_Color.md` 6번 참고).
5. 값이 변수 목록에 없는 경우(예: 범위 밖으로 분류된 마진 값, 또는 4/8 배수를 어기는 값)는 바인딩하지 않고 그대로 둔다 — 배수 규칙을 어기는 값은 임의로 보정하지 않고 사용자에게 먼저 보고한다.
6. 바인딩 후 일부 노드를 재조회해 `boundVariables`에 올바른 변수 id가 걸려 있는지 검증한다.

## 6. 오류 판정 기준

- Division Spacing 값이 4 또는 8의 배수가 아님
- Spacing Variables 이름이 실제 값과 다름 (의미 이름이 아니라 값 그대로 이름에 반영해야 함)
- 가이드 문서(룰러)의 사각형이 값 오름차순으로 정렬되지 않음
- 사각형 높이와 라벨 숫자가 일치하지 않음
- 가이드/Variables 어느 한쪽에만 값이 반영되고 다른 쪽은 누락됨
- 실사용 스캔 시 인스턴스 오버라이드 노드(`;` 포함 id)를 빠뜨려 실제 쓰이는 값을 놓침
- `SPACE_BETWEEN` 자동 계산값을 실제 spacing 토큰으로 착각해 포함시킴
- 가이드/Variables에서 값을 삭제하기 전 사용자 확인(및 바인딩 영향 스캔) 없이 임의로 삭제함
- 삭제 전 바인딩 영향 스캔 시 자식 노드만 확인하고 **마스터 컴포넌트 자신의 최상위 속성**(예: 마스터 프레임 자체의 padding)을 빠뜨림
- 프레임에 변수를 바인딩할 때 값이 정확히 일치하지 않는데 근사값으로 임의 바인딩함 (사용자 확인 없이)
- 반복되는 컴포넌트 인스턴스(내부 요소든 최상위 인스턴스 자신이든)에 마스터가 아닌 인스턴스별로 개별 바인딩함 — 일반 노드 스캔 시 `id`에 `;`가 없다고 무조건 "일반 노드"로 취급하면 최상위 인스턴스 자신을 놓친다(`type !== "INSTANCE"`도 함께 체크해야 함, 6-1번 참고)
- 일반 노드와 인스턴스 오버라이드 노드를 한 스크립트에서 같이 처리하다 롤백 오류 발생
- Variables 패널 순서가 값 오름차순을 따르지 않음

## 6-1. 마스터 우선 바인딩 시 흔한 실수 — 상위 인스턴스 자체를 놓침

일반 노드 스캔에서 `!n.id.includes(";")` 필터만 쓰면, **최상위 컴포넌트 인스턴스 자신**(예: `Footer`, `Question item`, `Tag`, `Board/Main/Question` 같은 top-level instance 노드. id에 `;`가 없어서 "일반 노드"로 분류됨)까지 걸러지지 않고 포함된다. 이 상태로 바로 `setBoundVariable`을 호출하면 **인스턴스에 로컬 오버라이드가 생겨 마스터 우선 규칙을 어기게 된다.**

- 반드시 `n.type !== "INSTANCE"`도 함께 체크해서, top-level 인스턴스는 일반 노드 패스에서 제외하고 마스터 해석 패스로 보내야 한다.
- 이미 실수로 인스턴스에 개별 바인딩해버린 경우: ① 인스턴스의 로컬 바인딩을 `setBoundVariable(field, null)`로 해제 → ② `getMainComponentAsync()`로 마스터를 찾아 마스터 쪽에 바인딩 → ③ 마스터가 `COMPONENT_SET`의 자식이면 형제 variant도 전부 확인해서 같은 가�을 가지면 함께 바인딩.
- 인스턴스 값이 마스터 값과 **다른 경우**(의도적인 로컬 커스터마이징)는 예외다 — 이때는 마스터로 옮기지 않고 그 인스턴스에 직접 바인딩하는 게 맞다(마스터와 다른 값을 마스터에 넣으면 다른 인스턴스들까지 값이 바뀌어버림).
- 검증 시 `n.boundVariables`를 노드 자기 자신에서만 확인하면 안 된다. 인스턴스/오버라이드 노드는 로컬 바인딩이 없어도 정상(마스터 상속)이므로, **실제 마스터까지 해석한 뒤 마스터의 바인딩 여부**로 검증해야 "이미 되어있는데 안 되어있다고 착각"하는 오탐을 피할 수 있다.

## 6-2. "Foundations" 컬렉션 — 현재는 유일한 소스(단일 소스 오브 트루스)

`03_Color.md` 10번 절차("Foundations" 컬렉션, 팔레트 문서용 계층형 네이밍)와 동일한 목적으로 처음에는 기존 `Spacing` 컬렉션과 별개의 **사본**으로 "Foundations" 컬렉션에 같은 값을 추가 등록했었다. 이후 마이그레이션을 거쳐 **기존 `Spacing` 컬렉션은 삭제되었고, 현재는 `Foundations` 컬렉션의 `Spacing/{값}` 변수들이 유일한 소스(single source of truth)다.** 아래는 현재 상태 기준 규칙이다.

- 변수명 형식은 기존과 동일하게 `Spacing/{값}`을 그대로 쓴다(예: `Foundations` 컬렉션 안의 `Spacing/24`). Figma Variables 패널에서 "Foundations" 컬렉션 탭 안에 `Spacing` 폴더로 묶여 표시된다.
- `scopes`는 `["ALL_SCOPES"]`로 설정한다.
- **더 이상 두 컬렉션이 공존하지 않는다.** 과거에는 기존 `Spacing` 컬렉션과 "Foundations" 컬렉션이 같은 값을 각각 별도로 들고 있어 값이 바뀔 때마다 양쪽에 반영해야 했지만, 마이그레이션 이후로는 `Foundations`만 갱신하면 된다 — 별도 동기화 대상이 없다.
- 새 프레임/노드에 Spacing을 바인딩할 때는 `Foundations` 컬렉션의 `Spacing/{값}` 변수를 사용한다(기존 `Spacing` 컬렉션은 삭제되어 더 이상 존재하지 않음).
- 이 마이그레이션의 절차·적용 이력은 아래 7번 표(마이그레이션 행) 및 `Style_Guide.md` 0번 공통 규칙을 참고.

## 6-3. 마스터 바인딩 후에도 인스턴스에 "죽은 오버라이드"가 남아 상속이 끊기는 문제

6-1번 실수(인스턴스에 개별 바인딩)를 `setBoundVariable(field, null)`로 "해제"한 뒤 마스터에 재바인딩해도, **인스턴스 쪽 오버라이드 기록 자체는 사라지지 않는다.** `setBoundVariable(field, null)`은 변수 연결만 지우고 그 필드의 숫자값을 그 시점의 값(예: 48)으로 인스턴스에 그대로 "고정"시키는데, Figma는 이 필드를 여전히 "로컬에서 명시적으로 건드린 값"(override)으로 취급한다. 그 결과:

- Figma UI(디자인 패널)에서 해당 속성에 변수 연결 아이콘(체인 아이콘)이 뜨지 않는다 — 겉보기엔 안 걸린 것처럼 보임.
- 값 자체는 마스터와 같아서 화면상 시각적 차이는 없다.
- 하지만 나중에 마스터의 변수 값이 바뀌어도 이 인스턴스는 따라가지 않는다(고정된 숫자값을 그대로 씀) — Variables를 쓰는 근본 목적(마스터 변경의 자동 전파)이 깨진 상태.

**진단 방법**: `instance.overrides` (읽기전용 배열)을 확인한다. `{ id, overriddenFields }` 형태로, 해당 인스턴스 서브트리 안에서 로컬로 오버라이드된 필드 목록을 알려준다. `boundVariables`가 비어있어도(값만 봐서는 정상 상속처럼 보여도) `overrides` 배열에 spacing 필드(`itemSpacing`/`padding*`/`boundVariables`)가 남아있으면 죽은 오버라이드다.

**해결 방법과 한계**: 플러그인 API에는 필드 단위로 오버라이드만 선택적으로 초기화하는 기능이 없다. `instance.resetOverrides()`는 그 인스턴스(및 하위 오버라이드 경로) 전체를 마스터 상태로 완전히 되돌리는 유일한 API이며, **텍스트 내용·이미지·색상·크기 등 다른 정상적인 오버라이드까지 전부 같이 날아간다.**

- 인스턴스(최상위 루트 기준)의 `overrides` 배열을 전수 확인해서, **spacing 관련 필드(`boundVariables`/`itemSpacing`/`padding*`/`counterAxisSpacing`/`clipsContent`) 외의 다른 필드가 전혀 없는 경우에만** `resetOverrides()`를 안전하게 쓸 수 있다.
- 유일한 예외: **`name` 필드만 추가로 섞여 있는 경우** — 레이어 이름은 `resetOverrides()` 직전에 값을 따로 기록해두고, reset 후 다시 `node.name = 기록값`으로 복원하면 이름을 잃지 않으면서 spacing 오버라이드만 제거할 수 있다.
- 그 외(텍스트 `characters`, `fills`, `height`/`width`, `cornerRadius`, `visible` 등 콘텐츠성 오버라이드가 섞인 경우)는 `resetOverrides()`를 쓰면 안 된다 — 반복되는 리스트 아이템(질문·태그·공지·뉴스 등)은 인스턴스마다 실제 콘텐츠가 다르기 때문에, 이런 인스턴스는 값은 지금 당장 맞지만(시각적으로 정상) **마스터 값이 바뀌어도 따라가지 않는 상태로 남는 것을 감수**하거나, Figma UI에서 사람이 직접 해당 속성만 우클릭 → "Reset value"로 필드 단위로 되돌리는 수작업이 필요하다(플러그인 API로는 불가능한, Text Style 정렬과 같은 종류의 UI-only 기능으로 추정됨).

### 6-3-1. 콘텐츠 보존형 `resetOverrides()` — 확장 기법과 실패 사례(영구 손실 경고)

위 6-3번은 "콘텐츠성 오버라이드가 섞이면 `resetOverrides()`를 쓰지 말라"고 안내하지만, Component 시맨틱 토큰(`Card`/`Tag`) 적용 작업에서 **텍스트 콘텐츠는 보존하면서 죽은 `boundVariables` 오버라이드만 제거해야 하는 상황**이 실제로 발생해, 아래 확장 기법을 시도했다. 이 기법은 부분적으로만 안전하다는 것이 이후 재검수 과정에서 확인됐다 — 아래 실패 사례를 반드시 함께 읽는다.

**확장 기법(저장 → reset → 복원)**: 대상 루트 인스턴스의 `overrides` 배열을 전수 확인해, `characters`/`name`/`visible`/`cornerRadius`/`letterSpacing`/`maxLines`/`textAutoResize` 필드가 있는 항목만 현재 값을 미리 별도로 저장해둔 뒤 `resetOverrides()`를 호출하고, 저장해둔 값을 같은 노드에 다시 써서 복원한다. 저장 전 해당 텍스트 노드에 `figma.loadFontAsync()`를 먼저 호출해야 한다.

**한계(반드시 인지할 것): `instance.overrides` 배열 자체가 실제 오버라이드를 누락 보고할 수 있다.** 이 세션에서 두 가지 사례로 확인됐다:

1. Card 안에 중첩된 Tag 서브 인스턴스(예: `I<Card id>;474:4793`)의 `topLeftRadius` 등 코너 반경 필드가 실제로는 로컬 값(`Foundations/Radius/4`)에 고정 바인딩돼 있었는데도, 루트 인스턴스의 `overrides` 배열에는 해당 필드가 전혀 나타나지 않았다(`overriddenFields`에 `"name"`만 표기). `resetOverrides()`를 이미 실행한 뒤에도 이 중첩 바인딩은 전혀 풀리지 않아 재확인 후 별도로 직접 재바인딩해야 했다(중첩 2단계 이상 깊이의 오버라이드는 `resetOverrides()`가 못 미치는 것으로 추정).
2. **더 심각한 사례 — 텍스트 `characters` 오버라이드 누락.** "답변 근거" 참고자료 카드 3개 중 2개(`776:4970`/`776:4971`)의 설명 텍스트가 `resetOverrides()` 이후 마스터 기본값("내용이 노출됩니다..." placeholder)으로 영구히 대체됐다. 원인 확인 결과, 같은 구조의 카드 3(`776:4972`)은 `overrides` 배열에 설명 텍스트 노드(`;700:12093`)의 `characters` 오버라이드가 정상적으로 잡혀 있었지만, 카드 1·2는 **같은 필드가 `overrides` 배열에 아예 나타나지 않았다.** 저장 스크립트는 `overrides` 배열에 있는 항목만 저장하므로 이 두 카드의 실제 인용문 원문은 저장되지 못한 채 `resetOverrides()`로 사라졌고, Figma 버전 기록에 접근할 방법이 없어 **복구가 불가능했다.**

**결론 및 향후 규칙**:
- `instance.overrides`는 오버라이드 존재 여부를 판단하는 **보조 신호일 뿐, 완전한 목록이라고 신뢰하면 안 된다.** 특히 (a) 2단계 이상 중첩된 서브 인스턴스의 바인딩 필드, (b) 텍스트 `characters` 필드에서 누락 사례가 확인됐다.
- **반복 리스트 아이템처럼 실제 텍스트 콘텐츠(질문·답변·인용문 등)를 담고 있는 인스턴스에는, `overrides` 배열만 믿고 `resetOverrides()`를 쓰지 않는다.** 부득이하게 써야 한다면, 실행 전 대상 서브트리의 **모든 TEXT 노드의 `characters` 값을 `overrides` 배열 참고 없이 전수(무조건) 저장**해두고 복원한다 — "오버라이드로 표기된 것만" 저장하는 방식은 안전하지 않다.
- 그래도 6-3번이 제시한 원칙(콘텐츠성 오버라이드가 섞인 인스턴스는 애초에 `resetOverrides()` 대상에서 제외하고, Figma UI의 필드 단위 "Reset value" 수작업으로 처리)이 여전히 가장 안전하다 — 특히 되돌릴 수 없는 실제 서비스 콘텐츠(법률 인용문 등)가 걸린 경우.
- 이 사고는 사용자가 스크린샷으로 변경 전/후를 직접 비교해 알려줘서 발견됐다 — 시각적으로 "카드가 있고 텍스트도 있다"는 이유로 정상이라 판단하지 않고, 실제 문구가 원본과 같은지까지 확인해야 한다는 교훈.

## 6-4. 가이드 문서 현행화(Variables와 일치 여부 점검) 절차

"이 가이드 프레임이 Variables에 등록된 값과 일치하는지 확인하고 현행화해줘" 같은 요청을 받았을 때 따르는 점검 절차다. 값을 등록·바인딩하는 5~6번 절차와 달리, **이미 만들어진 가이드 문서가 최신 Variables 상태를 제대로 반영하고 있는지 감사(audit)하고 어긋난 부분만 고치는** 작업이다.

1. 대상 가이드 프레임(예: "05 Spacing")의 룰러 다이어그램 사각형들을 전수 스캔해 각 사각형의 `height`와 옆 라벨 텍스트를 확인한다.
2. `figma.variables.getLocalVariableCollectionsAsync()`로 현재 `Foundations` 컬렉션의 `Spacing/{값}` 변수 목록(이름·값)을 가져와 1번과 비교한다.
   - **값 자체가 다르면**(가이드에 없는 값, 또는 Variables에 없는 값) 자동으로 추가·삭제하지 않고 먼저 사용자에게 보고한다.
   - **값은 일치하는데 `boundVariables`가 비어있으면**(사각형이 숫자만 같고 실제 변수에 연결돼 있지 않은 상태) 곧바로 `rect.setBoundVariable("height", variable)`로 바인딩한다 — 값이 이미 맞으므로 시각적 변화가 없는 안전한 작업이라 확인 없이 진행 가능하다.
3. 같은 방식으로 관련된 다른 가이드 프레임(예: "06 Radius")도 필요시 함께 점검한다 — Radius는 `topLeftRadius`/`topRightRadius`/`bottomLeftRadius`/`bottomRightRadius` 4개 필드와 `boundVariables`를 확인한다(`06_Radius.md` 6-1번 참고).
4. **레이어(프레임) 이름이 실제 내용과 다른 경우도 함께 확인한다.** 가이드 프레임을 복제·재활용하는 과정에서 레이어명이 갱신되지 않고 남아있는 경우가 있다(예: 내용은 "06 Radius"인데 프레임명이 예전 "04 Font" 그대로 남아있던 사례). 제목 텍스트(타이틀)를 기준으로 프레임명이 다르면 사용자에게 알리고, 요청하면 제목과 일치하도록 이름을 바로잡는다.
5. 바인딩을 새로 건 뒤에는 `get_screenshot`으로 값 변경 전후 시각적으로 동일한지 확인한다.
6. 파일 안에 같은 이름의 가이드 프레임이 여러 페이지/좌표에 중복 존재할 수 있다(예: "★ Style Guide" 페이지 안에도 서로 다른 node-id로 같은 "05 Spacing"이 여러 벌 있었던 사례). 사용자가 준 Figma URL의 node-id를 정확히 그 프레임에 한정해서 점검하고, 다른 사본까지 임의로 같이 고치지 않는다(별도 요청 시에만 확장).
